# AI 참가자 설계

작성일: 2026-09-14 · 대상: 2차 (3단계 중 둘째) · 선행: [1차 펀더멘털 앵커](2026-09-14-fundamentals-anchor-design.md)

## 1. 무엇을 만드나

혼자 하던 게임에 **매매하는 AI 참가자**가 들어온다. 이들이 뉴스에 반응해 사고팔고, 그 주문이 가격을 밀고, 체결이 피드로 흐른다.

목적은 둘이다.

1. **3차 종토방의 전제.** 종토방은 AI 참가자가 쓴다. 포지션과 성향이 있어야 글이 나온다.
2. **뉴스를 읽는 두 번째 방법.** 김부장이 매번 낚이는 성향이라면, 어떤 기사에 **김부장만** 들어간 것은 함정의 신호다. 숫자가 아니라 **신원**을 읽는 것이다.

## 2. 범위 — 안 깨는 것만

`api.md` 2부의 v2 7개 중 **다섯 개**만 한다.

| | 항목 | 이번에 | 프론트 계약 |
|---|---|---|---|
| A | AI 참가자 | ● | 필드 추가 |
| B | 주문 흐름의 가격 영향 | ● | 변화 없음 (가격만 바뀜) |
| C | 거래량 집계 | ● | 필드 추가 |
| F | 체결 피드 | ● | 필드 추가 |
| G | AI 수 설정 | ● | 기본값 5로 하위호환 |
| D | 목표 판정을 현금으로 | ✕ | **`goal_reached`·`target` 의미 변경** |
| E | 게임 종료와 순위 | ✕ | **`status`·`ranking`·`winner` 신설** |

**D·E 를 미루는 이유는 프론트가 지금 1부 계약 위에서 만들어지고 있기 때문이다.** 둘은 진행바·라운드 전환·목표 판정을 전부 다시 만들게 한다. 종토방에 필요한 것은 A 뿐이므로, D·E 는 프론트가 v1 로 한 바퀴 돈 뒤 백엔드와 함께 옮긴다.

그래서 `api.md` §13 의 미해결 항목 두 개가 자동으로 정리된다 — **라운드는 유지**되고(D·E 를 미루니 `next-round` 가 그대로 산다), 가격 이력·평단은 프론트 쪽 결정이라 이 문서 밖이다.

## 3. 결정론이 구조를 정한다

서버에 타이머가 없다. 탭을 30분 비웠다 돌아오면 1,800 tick 이 한 요청에서 진행되고, **AI 매매도 그 안에서 재생**된다. `api.md` §12 가 말하는 *"(시드, tick, 뉴스)의 결정론적 함수"* 다. LLM 은 쓸 수 없다 — 재생이 안 되고, 따라잡기 요청에서 1,800번 부를 수도 없다.

그런데 AI 매매가 가격을 밀면(B), 매매는 `engine.advance` 의 tick 루프 **안에서** 일어나야 한다. 매수가 그 tick 의 가격을 바꾸고, 그것이 다음 tick 의 AI 판단에 들어간다.

### 콜백으로 경계를 지킨다

```python
def advance(state, plans, to_tick, rng, on_tick=None) -> None:
    for tick in range(state.last_tick + 1, to_tick + 1):
        ...노이즈 → 앵커 → 램프...
        _decay_flow(state)
        if on_tick is not None:
            for symbol, value in on_tick(tick).items():
                add_flow(state, symbol, value)
```

`engine` 은 *"이 tick 에 각 종목이 순매수 N 원어치"* 만 받는다. **누가 왜 샀는지는 모른다.** 매매 규칙은 새 모듈 `app/participants.py` 가 소유하고 `main._sync` 가 둘을 잇는다.

`on_tick` 이 `None` 이면 지금과 완전히 같게 동작한다. 기존 테스트가 그대로 산다.

`PriceState` 에 `flow_log: dict[str, float]` 가 하나 더 붙는다. `start_price` 와 `anchor_log` 옆이다.

### tick 안의 순서

이 순서가 곧 규칙이다.

| | 단계 | 왜 이 자리인가 |
|---|---|---|
| 1 | 노이즈 | 난수를 소비하는 유일한 단계 |
| 2 | 앵커 | 1차. 난수를 안 쓴다 |
| 3 | 뉴스 램프 | 난수를 안 쓴다 |
| 4 | 주문 흐름 **감쇠** | 새 주문을 받기 전에 먼저 식힌다 |
| 5 | `on_tick(tick)` | **AI 가 여기서 가격을 읽고 매매한다** |
| 6 | 주문 흐름 **반영** + 상한 | 5 가 만든 순주문량을 가격으로 옮긴다 |

**5 가 6 보다 앞인 것이 중요하다.** AI 는 자기 주문이 가격을 밀기 *전* 가격을 보고 판단한다. 반대로 두면 자기 체결의 영향을 미리 보고 사는 셈이 되어, 같은 tick 안에서 되먹임이 생긴다.

### 난수를 engine 과 섞지 않는다

AI 판단이 `engine.advance` 의 `rng` 를 소비하면 **증분 계산과 일괄 계산이 어긋난다** — AI 가 매매한 tick 과 안 한 tick 의 난수 소비량이 달라지기 때문이다. 그 불변식은 이 서버에서 가장 중요한 성질이다.

그래서 AI 는 자기 난수를 쓴다:

```python
def _roll(seed: int, ai_index: int, news_id: int) -> float:
    return random.Random((seed * 1_000_003) ^ (news_id * 31) ^ (ai_index * 7)).random()
```

tick 진행 순서와 무관하게 같은 값이 나온다. 세션은 `ai_seed: int` 를 하나 들고 있으면 된다.

## 4. 주문 흐름 — 감쇠하는 별도 항

`api.md` §12 가 경고한다: *"AI 가 상승에 반응해 사고 그 매수가 가격을 또 올리면 무한 나선이 된다."*

누적 로그수익에 영구히 더하면 그 나선이 생긴다. 그래서 **따로 들고 매 tick 0 으로 감쇠**시킨다.

```python
state.flow_log[symbol] *= (1.0 - config.FLOW_DECAY)          # 먼저 식히고
state.flow_log[symbol] += FLOW_IMPACT_PER_MILLION * value / 1_000_000
state.flow_log[symbol] = clamp(state.flow_log[symbol], ±config.FLOW_MAX)

price = start_price[s] * exp(log_return[s] + flow_log[s])
```

주문 충격이 **일시적**이다. 큰 주문은 불리하게 체결되고 곧 회복된다 — §12 가 말한 *"슬리피지가 자연히 생긴다"* 가 공짜로 나온다. 플레이어의 주문에도 똑같이 적용된다.

### 상한이 "조역" 을 구조적 보장으로 만든다

§12 는 감쇠와 *"모멘텀 추종형 AI 비중 제한"* 두 가지를 요구했다. 이 설계의 AI 는 전원 뉴스 반응형이라 모멘텀 추종이 없지만, 그것은 명단을 고치면 깨지는 약속이다. **상한을 걸면 명단과 무관하게 깨지지 않는다.**

| 상황 | 원값 | 실제 |
|---|---|---|
| 1명이 35만원 매수 | +1.05% | +1.05% |
| 3명이 105만원 | +3.1% | **+3.0%** |
| 9명이 495만원 | +14.8% | **+3.0%** |

전형적 뉴스 임팩트 10% 대비 **최대 30%** — §12 의 "20~30%" 에 정확히 맞는다. 반감기는 약 4.6 tick 이라 단발 주문은 5초면 절반이 식는다.

가장 약한 뉴스(5%) 대비로는 60% 까지 갈 수 있다. **의도한 것이다** — 약한 재료는 군중에 묻혀야 한다. 다만 그 군중 자체가 뉴스에 반응해 생기므로 뉴스를 뒤집지는 않는다.

## 5. AI 명단 — 피라미드 + 엇박자 2명

파라미터 넷은 §12 그대로다.

| | id | 이름 | 통찰력 | 반응 | 베팅 | 익절 | 성격 |
|---|---|---|---|---|---|---|---|
| 1 | `jung` | 정소장 | 0.90 | 3t | 35% | 12% | 진짜 고수 |
| 2 | `han` | 한실장 | **0.88** | 4t | 45% | **60%** | **엇박자 — 다 맞히는데 안 판다** |
| 3 | `oh` | 오과장 | 0.60 | 5t | 30% | 15% | 중간 |
| 4 | `bae` | 배차장 | 0.55 | 8t | 25% | 10% | 중간, 소심 |
| 5 | `moon` | 문대리 | 0.50 | 6t | 40% | 18% | 중간 |
| 6 | `shin` | 신주임 | 0.45 | 7t | 20% | 14% | 중간 |
| 7 | `kang` | 강사원 | **0.25** | **1t** | 50% | 8% | **엇박자 — 몰라도 제일 빠르다** |
| 8 | `kim` | 김부장 | 0.22 | 9t | 55% | 40% | 물리는 역할 |
| 9 | `park` | 박선배 | 0.20 | 6t | 60% | 25% | 몰빵형 |

`ai_count` 가 N 이면 **위에서 N 명**을 쓴다. 기본 5 면 정소장·한실장·오과장·배차장·문대리 — 고수 2 와 중간 3 이라 초보 난이도로 적당하고, 9 로 올리면 호구들이 들어와 체결 피드가 시끄러워진다.

**순위가 통찰력 순서와 어긋난다.** 한실장은 계속 옳은 종목을 사면서도 익절을 못 해 현금이 안 쌓이고, 강사원은 통찰력 꼴찌인데 1 tick 반응으로 램프 초반을 먹는다. §12 의 *"옳게 고르는 것과 이기는 것은 다르다"* 가 명단에서 나온다.

이름은 **3차 종토방에서 계속 쓰인다.** 여기서 정한 성격이 곧 그 목소리다.

## 6. AI 한 명의 매 tick

```
1. 이 tick 이 반응 예정일인 뉴스가 있으면
     통찰력 판정 성공 → 실제 impact 부호대로 행동
     실패            → surface_tone 대로 행동  (그래서 낚인다)

   호재로 봤다 → 현금의 bet_ratio 만큼 매수
   악재로 봤다 → 그 종목 보유분 전량 매도  (공매도 없음)

2. 보유 종목의 수익률이 익절선을 넘으면 전량 매도

3. 현금도 보유도 없으면 아무것도 안 한다
```

- 뉴스가 tick T 에 등장하면 각 AI 는 `T + reaction_ticks` 에 한 번 판단한다. 같은 뉴스를 두 번 보지 않는다.
- AI 는 **플레이어와 같은 규칙**이다 — 시드 100만, 양방향 수수료 0.2%, 같은 가격.
- **노가다는 없다.** 그것은 플레이어 전용 구제 장치다. 파산한 AI 는 리더보드에 남되 매매를 멈춘다.
- 익절 판정에 평단이 필요하므로 AI 보유는 `{symbol: (qty, total_cost)}` 로 든다.

### 통찰력이 보는 것

성공하면 `plan.impact` 의 **부호만** 본다. 크기는 안 본다 — 크기까지 알면 고수 AI 가 완벽해져 플레이어가 따라잡을 수 없다.

`kind` 가 `exaggerated`(임팩트 0~1.5%)인 경우 부호는 표면 톤과 같으므로, 통찰력이 높아도 **약한 재료에 들어가는 것을 막지 못한다.** 의도한 것이다 — 과장 기사는 원래 판별이 아니라 크기의 문제다.

## 7. 응답 (전부 추가)

### 스냅샷에 붙는 필드

```json
{ "ai": [ { "id": "han", "name": "한실장", "cash": 1340000,
            "equity": 1820000, "rank": 2 } ],
  "trades": [ { "seq": 41, "tick": 137, "actor": "김부장",
                "symbol": "geno", "name": "제노셀",
                "side": "buy", "qty": 20, "price": 47850 } ],
  "stocks": [ { "volume": 340, "volume_avg": 62 } ] }
```

**보유 종목은 공개하지 않는다.** 체결 피드를 성실히 읽으면 재구성할 수 있고, 그건 주의 깊은 플레이어의 정당한 우위다.

**순위는 `equity` 기준이다.** 동점이면 명단 순서로 가른다 — 임의로 흔들리면 리더보드가 매 폴링마다 요동친다. §11 은 `cash` 로 적었지만 그것은 D(목표를 현금으로)가 들어간 뒤의 이야기다. D 를 미뤘으므로 지금 성과의 잣대는 v1 과 같은 총자산이어야 한다. `cash` 도 함께 실어 D 가 들어올 때 잣대만 바꾸면 되게 한다.

`volume` 은 최근 `VOLUME_WINDOW_TICKS`(60) 구간의 체결 수량이고, `volume_avg` 는 그때까지의 구간 평균이다. *"평소의 5배"* 를 프론트가 계산할 수 있게 하는 값이다.

### 요청 변경

| | 무엇 |
|---|---|
| `POST /api/game` | 본문 `{"ai_count": 5}` 선택. 1~9, 기본 5. **본문 없이 보내도 된다** |
| `GET /api/state` | 쿼리 `trades_since` 추가. 기본 −1. `since` 와 같은 방식 |

### 새 오류 코드

| 코드 | 상태 | 언제 |
|---|---|---|
| `bad_ai_count` | 400 | `ai_count` 가 1~9 밖 |

`game_finished` 는 E 와 함께 미룬다 — 종료 개념이 아직 없다.

## 9. 테스트

기존 원칙 그대로 — **네트워크도 Claude 도 부르지 않는다.**

| | 무엇 | 왜 |
|---|---|---|
| 1 | **AI 매매가 있어도 증분/일괄이 같다** | 이 작업에서 가장 깨지기 쉽다. 1,800 tick 따라잡기가 500ms 폴링과 같아야 한다 |
| 2 | 같은 `ai_seed` 는 같은 매매 기록을 낸다 | 재현 없이는 밸런스를 못 고친다 |
| 3 | 통찰력 1.0 은 역방향 함정에 안 낚이고, 0.0 은 항상 낚인다 | 파라미터가 실제로 작동하는가 |
| 4 | 주문 흐름이 0 으로 감쇠한다 | 나선이 안 생긴다 |
| 5 | 주문 흐름이 `FLOW_MAX` 를 절대 안 넘는다 | "조역" 의 구조적 보장 |
| 6 | 주문 흐름 없이도 `on_tick=None` 이면 기존과 동일 | 회귀 방지 |
| 7 | AI 가 파산해도 서버가 안 죽고 매매만 멈춘다 | |
| 8 | AI 는 노가다를 하지 않는다 | 플레이어 전용 구제 장치다 |
| 9 | `trades[]` 가 `trades_since` 로 정확히 걸러진다 | |
| 10 | 플레이어 체결도 `actor: "you"` 로 흐른다 | |
| 11 | 스냅샷에 AI **보유 종목**이 없다 | §7 |
| 12 | `ai_count` 경계 (0, 1, 9, 10) | |
| 13 | 본문 없는 `POST /api/game` 이 기본 5명으로 돈다 | 하위호환 |
| 14 | 거래량 창이 오래된 체결을 버린다 | |
| 15 | 앵커·램프·노이즈가 주문 흐름과 함께 돌아도 각각 유효하다 | 1차와의 상호작용 |

1번이 이 작업의 중심이다. 기존 `test_incremental_advance_matches_one_big_advance` 를 AI 가 붙은 상태로 확장한다.

## 10. 미룬 것

| 무엇 | 언제 |
|---|---|
| D 목표를 현금으로 · E 종료와 순위 | 프론트가 v1 로 한 바퀴 돈 뒤, 프론트와 **함께** |
| 종토방 | 3차. 이 문서의 명단과 성향 위에 얹힌다 |
| AI 의 기업분석 사용 | 지금 AI 는 펀더멘털을 안 본다. 넣으려면 성향에 축이 하나 더 생긴다 — 3차 이후 |

마지막 항목은 1차와 자연스럽게 이어지는 확장이라 적어 둔다. *"이 AI 는 재무를 보고 저 AI 는 뉴스만 본다"* 는 축이 생기면 종토방 글이 더 입체적으로 나온다. 다만 지금 넣으면 파라미터가 다섯이 되어 밸런스를 잡기 어렵다.

## 11. 결정하지 않은 것

여기 숫자는 **플레이해보며 조정한다.**

1. `FLOW_IMPACT_PER_MILLION = 0.03`, `FLOW_DECAY = 0.15`, `FLOW_MAX = 0.03` — §4 의 계산이 근거지만 체감은 다를 수 있다
2. 명단 9명의 파라미터 — 순위가 통찰력과 어긋나는 것만 지키면 나머지는 자유롭다
3. `VOLUME_WINDOW_TICKS = 60` — 짧으면 튀고 길면 둔하다
4. 기본 `ai_count = 5` — 체결 피드가 읽을 만한 밀도인지가 기준이다
